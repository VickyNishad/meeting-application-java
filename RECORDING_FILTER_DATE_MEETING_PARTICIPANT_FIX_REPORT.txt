--------------------------------------------------------------------------------
1. ROOT CAUSES
--------------------------------------------------------------------------------
a) The Meeting dropdown ignored the date.
   - GET /api/v1/speech-recordings/facets returned dates, meetings and
     participants as three unrelated lists. A meeting option had no date.
   - SpeakingClips.tsx always rendered every meeting, and changing the date
     never reset the selected meeting.
   - On the real data, choosing 03-11-2026 still offered all 5 meetings, although
     only IND VS ZM has clips that day. Date + another meeting silently gave an
     empty list.
b) The Participant dropdown ignored the date.
   - It already followed the meeting (previous fix), but with a date selected
     and "All meetings" it showed participants from every date.
   - A participant who had no clips on the new date stayed selected.
c) Participant options carried no host information, so "(Host)" could not be
   shown.
d) Not a cause: time zones. Dates are the clip's folder date (DD-MM-YYYY = clip
   start in the MEETING's time zone, SpeechClipStorage.relativePath). The list
   filter matches the same folder prefix, and the web code handles dates as
   plain YYYY-MM-DD strings (no Date/UTC conversion). The convention was kept.

2. DATABASE RELATIONSHIPS USED (no schema change, nothing invented)
--------------------------------------------------------------------------------
speech_recordings.participant_id      -> meeting_participants.id
                                         (one participation in one meeting)
speech_recordings.meeting_id          -> meetings.id
speech_recordings.storage_path        first 10 chars = folder date DD-MM-YYYY
speech_recordings.host_id             = meetings.host_id, stored on the clip
                                         when it is created
speech_recordings.participant_user_id = meeting_participants.user_id
                                         (null for guests)

Participant options remain clip-based, as approved earlier: people who joined
but never produced a clip are not offered.


--------------------------------------------------------------------------------
3. HOST IDENTIFICATION
--------------------------------------------------------------------------------
host = (speech_recordings.participant_user_id = speech_recordings.host_id)

- This is the same rule the app uses to give the HOST role when someone joins
  (MeetingAccessService.isHost: meetings.host_id equals the user's id).
- It is computed per clip, so it is per meeting.
- Guests (no account) are never host. No names are compared, and no user is
  hardcoded.
- Checked on the real data: the rule matches meeting_participants.role = HOST in
  all 15 meeting/participant pairs. Vicky Nishad is host of all 5 meetings and
  nobody else is.
- The API returns the plain name plus host=true/false. The web adds " (Host)"
  exactly once.

5. API CHANGES (existing endpoint, add-only, backward compatible)
--------------------------------------------------------------------------------
GET /api/v1/speech-recordings/facets?view=hosted|mine

  meetings[]:     { id, label, dates: ["YYYY-MM-DD", ...] }
                  (dates added)
  participants[]: { id, label, meetingId, host: true|false, dates: [...] }
                  (host and dates added)
  dates[]:        unchanged

Nothing removed or renamed, and label is still the plain name. Authorization is
unchanged: hosted = meetings the user hosts; mine = the user's own clips.


--------------------------------------------------------------------------------
6. FRONTEND CHANGES (SpeakingClips.tsx)
--------------------------------------------------------------------------------
- Meeting options: only meetings with clips on the selected date.
- Participant options: only participations with clips in the selected meeting
  AND on the selected date.
- Labels:
  - "Name (Host)" for the meeting's host.
  - While no meeting is selected: "Name (Host) · Meeting title" (option a).
- Changing the date (dropdown or calendar):
  - clears the meeting if it has no clips that day
  - clears the participant if they are no longer valid
  - keeps valid selections
- Changing the meeting: clears an invalid participant.
- Clearing a filter (choosing "All dates" or "All meetings"): all options return,
  and valid selections are kept.
- Empty states: "No meetings on this date", "No participants on this date",
  "No participants in this meeting".
- Loading: "Loading meetings…" / "Loading participants…" (selects disabled).
- Errors: the existing alert with Retry.
- Options are filtered locally from one facets response, so there are no extra
  requests or out-of-order responses.

9. INDEPENDENT QA FINDINGS (separate QA agent; NOT fixed - awaiting approval)
--------------------------------------------------------------------------------
Verdict: the filtering logic is correct.
- Facets vs list results: 182 live combinations, 0 mismatches.
- Time zones: folder dates match the meeting's time zone for all 293 clips.
- Resets, JSON compatibility, playback and download: OK.
The problems are in the labels.

QA-1 HIGH, CONFIRMED (test case; can happen with real use)
     A host who leaves and rejoins after the reconnect window (30 s) gets a new
     participation, so "Vicky Nishad (Host)" can appear twice in one meeting.
     - Cause: each participation is a separate option (the approved
       one-participant-per-participation rule).
     - Needs your decision: merge a person's participations in one meeting into
       one option (the list filter would then use the person, not the
       participation), or distinguish them in the label (e.g. the time of their
       first clip).
QA-2 MEDIUM, CONFIRMED
     A guest can name themselves "Vicky Nishad (Host)". host=false is correct,
     but the label looks exactly like the real host's.
     - Suggested: strip or reject "(Host)" in guest names at join, or mark
       guests, e.g. "(Guest)".
QA-3 MEDIUM, CONFIRMED on real data
     Identical entries that cannot be told apart.
     - PK VS IND has two guest participations named "Sandeep" (3 and 6 clips),
       so "Sandeep" is shown twice.
     - The test account has 3 meetings titled "AQH_fan_on_reload", shown 3
       times.
     - Suggested: add a distinguishing detail (first-clip or meeting time).
QA-4 LOW, CONFIRMED
     One storage_path that does not start with "DD-MM-YYYY/" makes the whole
     facets call fail (HTTP 500).
     - The app never writes such paths (all 293 rows are valid).
     - Suggested: skip values that do not parse.
QA-5 LOW, CONFIRMED
     If loading the filter options fails and a date is then picked, the selects
     say "No meetings on this date" although the real reason is the error (the
     alert with Retry is shown).
     - Suggested: "Filters unavailable" while in error.
QA-6 LOW, existed before
     With filters set and no matches, the empty text still says "Clips are
     recorded in meetings with automatic recording turned on" instead of
     "no clips match the filters".
QA-7 INFO  Facets queries sort and group in memory. About 0.2 s at 200k clips
           for one host (fine now: 293 rows). A covering index or payload cap
           could come later.
QA-8 INFO  Disabled selects explain themselves only through their first
           option text (no aria-describedby).
QA-9 INFO, existed before
           The calendar's latest selectable date uses the browser's time zone;
           folder dates use the meeting's.
QA-10 INFO Selections are not re-checked when the options reload. Harmless
           today, because clips are never deleted.
QA-11 INFO Same-name participants under "All meetings" have no tie-break sort
           (order may vary).
