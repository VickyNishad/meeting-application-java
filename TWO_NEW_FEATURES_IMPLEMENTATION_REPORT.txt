2. FEATURES ADDED
--------------------------------------------------------------------------------
Feature 1 - environment-based storage for speaking clips
  RECORDING_STORAGE_TYPE=LOCAL (default; the dev profile and local Docker)
    Behaviour is identical to before. Clips are written to RECORDING_LOCAL_PATH
    (falls back to the existing RECORDING_STORAGE_PATH):
      D:\MeetingApplication\Recordings\DD-MM-YYYY\<Meeting>\<Participant>\DDMMYYHHmmss_<id>.webm
  RECORDING_STORAGE_TYPE=S3 (production; the prod profile defaults to S3)
    1. Chunks are written to the local folder exactly as before (it is now a
       staging folder), then finalized and verified as WebM by the existing code.
    2. The verified file is uploaded to s3://AWS_S3_BUCKET/[AWS_S3_PREFIX/]<same relative path>.
    3. Only then is the clip marked COMPLETED (or INCOMPLETE by recovery).
    4. The staged file is deleted after the database commit.
    If the upload fails: the API returns 503, the clip stays RECORDING with its
    verified local file, and either a retried finish or the existing
    once-a-minute recovery job completes it once S3 is reachable again.
    Playback and download keep the same API (access-url, then the signed
    /content link). That link now redirects (302) to a presigned S3 URL that
    lasts no longer than the signed link.

Feature 2 - active speaker green border
  Already implemented in the existing application (found during analysis):
  LiveKit server-side voice activity detection, a 3px green frame per tile,
  several speakers at once, an immediate off on mute or disconnect, a
  stale-event guard after unmute, clearing on reconnect, per-tile re-renders,
  and respect for the visibility modes. The only addition: the silence
  threshold is configurable with VITE_SPEAKING_RELEASE_MS (0-10000 ms,
  default 600). Recording is not affected: speaking clips pass their own
  threshold (CLIP_RELEASE_MS) to the shared hook.

4. STORAGE CONFIGURATION INSTRUCTIONS
--------------------------------------------------------------------------------
Local development (Windows)
  Without Docker (start-local.ps1, dev profile): nothing to set. The default is
    D:/MeetingApplication/Recordings. Override with RECORDING_LOCAL_PATH.
  Docker Desktop: in .env
    RECORDING_STORAGE_TYPE=LOCAL
    RECORDING_LOCAL_PATH=D:/MeetingApplication/Recordings
  The folder is created on first use.

Production (Linux)
  .env (Docker) or environment (java -jar with SPRING_PROFILES_ACTIVE=prod):
    SPRING_PROFILES_ACTIVE=prod
    RECORDING_STORAGE_TYPE=S3          # empty also means S3 with the prod profile (QA-4)
    AWS_REGION=ap-south-1              # your region
    AWS_S3_BUCKET=your-private-bucket
    AWS_S3_PREFIX=speech-recordings    # optional
    AWS_ACCESS_KEY_ID= / AWS_SECRET_ACCESS_KEY=   # leave empty to use an IAM role (recommended)
    RECORDING_LOCAL_PATH=/srv/meetly/recording-staging   # staging folder on local disk
  At startup the log shows "Speaking clips are uploaded to s3://<bucket>/<prefix> (IAM role credentials)"
  (or "access-key credentials"). If the bucket is missing or unreachable, an error is logged.
  Production without AWS_REGION/AWS_S3_BUCKET refuses to start; it never falls back to local disk silently.
  Moving an existing installation from LOCAL to S3: copy the earlier clips once, then switch:
    aws s3 sync <RECORDING_LOCAL_PATH> s3://<bucket>/<prefix> --exclude "*.part"

5. S3 SETUP REQUIREMENTS
--------------------------------------------------------------------------------
- Create the bucket yourself, in AWS_REGION. The application never creates it.
- Turn on "Block all public access". There is no bucket policy for anonymous
  access and no ACLs; playback uses presigned URLs only.
- Default encryption: SSE-S3 (or SSE-KMS; then also grant kms:Decrypt and
  kms:GenerateDataKey to the role).
- Bucket CORS is not needed: browsers follow redirects in <video>/<audio> and
  in the download link, and no fetch() is used.
- IAM policy for the server's role (or the key's user), least privilege:
    s3:PutObject, s3:GetObject  on  arn:aws:s3:::your-private-bucket/speech-recordings/*
    s3:ListBucket               on  arn:aws:s3:::your-private-bucket   (startup existence check)
- Instance metadata (EC2): IMDSv2 hop limit 2 when the API runs in Docker.
- Optional: a lifecycle rule for retention, and versioning against accidental
  overwrite.

7. INDEPENDENT QA FINDINGS AND RESOLUTION
--------------------------------------------------------------------------------
QA-1  HIGH - CONFIRMED - FIXED.  IAM-role credentials never worked.
      Cause: ChainedProvider(AwsEnvironmentProvider, IamAwsProvider). MinIO's
      chain only skips a provider on ProviderException, but
      AwsEnvironmentProvider throws NullPointerException (keys unset) or
      IllegalArgumentException (keys empty, as docker-compose passes them).
      The chain aborted before the IAM role was tried. Reproduced with a
      standalone program against minio 8.6.0 (both cases aborted).
      Fix: IamAwsProvider is used on its own when no keys are configured;
      configured keys use StaticProvider.
      Evidence:
        - SpeechClipCredentialsTest: static keys are fetched as configured; for
          null, empty, blank or half-set keys the provider is exactly
          IamAwsProvider (not a chain).
        - End-to-end check (manual, scratchpad program): no keys configured,
          AWS_CONTAINER_CREDENTIALS_FULL_URI pointing at a local stand-in for
          the ECS task-role endpoint, real SpeechClipObjectStore -> MinIO:
          "credential endpoint calls=1 uploaded size=7 presigned GET=200
          IAM_ROLE_PATH_OK". The EC2 instance-profile (IMDSv2) and EKS
          web-identity variants use the same provider but were not exercised.
      The weak test "withoutKeysTheIamRoleChain..." was replaced; it had only
      checked construction.

QA-2  MEDIUM - FIXED.  The upload runs inside the finish transaction.
      Fix: the S3 client now uses 10 s connect and 2 min read/write timeouts
      instead of OkHttp's 5-minute defaults, so a stalled S3 frees the
      connection quickly. The clip stays RECORDING and is retried.
      Evidence: unit test "unreachable bucket -> STORAGE_UNAVAILABLE" (fast
      failure) and the full suite. A slow-network soak test was not run.

QA-3  MEDIUM - DOCUMENTED.  LOCAL -> S3 switch: earlier clips exist only on disk.
      Fix: a migration step ("aws s3 sync ... --exclude *.part"; the layout is
      identical) in .env.example, docs/07-deployment.md and section 4 of
      this report. No code change (no schema change, as planned).

QA-4  MEDIUM - FIXED.  Compose defaulted to LOCAL, overriding the prod default.
      Fix: compose passes RECORDING_STORAGE_TYPE through empty when unset; an
      empty value means S3 with the prod profile, LOCAL otherwise. Production
      without a bucket now refuses to start instead of silently using local
      disk. An explicit LOCAL in production is honoured with a warning.
      Evidence: SpeechClipObjectStoreTest "anEmptyTypeFollowsTheProfile..."
      and "theProductionProfileDefaultsToS3"; docker compose config renders
      your local .env as LOCAL with the D:/MeetingApplication/Recordings mount.

QA-5  LOW - ACCEPTED (no change).  A permanently failing upload is retried
      every minute with a warning, and the free-space check eventually
      protects the disk. This is the existing rule for storage errors.
      Recommendation: alert on "Could not recover speaking clip" log lines or
      on the number of RECORDING clips older than 10 minutes.

QA-6  LOW - ACCEPTED (no change).  Empty staging folders remain after upload.
      Harmless; can be cleaned with a periodic find -type d -empty -delete.

QA-7  LOW - FIXED.  S3 test with non-Latin names.
      Evidence: SpeechRecordingS3StorageIntegrationTest
      "nonLatinMeetingAndParticipantNames..." (meeting "साप्ताहिक बैठक",
      participant "आशा देवी"): key .../साप्ताहिक_बैठक/आशा_देवी/..., the object
      size matches, and the presigned download returns 200 with the WebM bytes.

QA-8  INFO.  Active speaker was already implemented; only the threshold became

QA-9  INFO.  Cloud recordings (Egress) are unchanged (out of scope by the default
