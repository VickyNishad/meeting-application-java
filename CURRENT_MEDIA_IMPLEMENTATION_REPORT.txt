SUMMARY
  - The browser talks to LiveKit directly. The Java backend never touches media. It decides who may do what, signs
    tokens, and pushes changed permissions to LiveKit.
  - Host permissions are enforced by the LiveKit server, not by the browser.
  - Speaking clips are recorded in each participant's browser and uploaded to the backend in chunks.
  - Whole-meeting cloud recording uses LiveKit Egress. It has never worked in this environment.
  - ROOT CAUSE OF ITEM 11 (see section 11): the recorder's browser runs in its own container, but LiveKit tells it to
    send media to 127.0.0.1 (LIVEKIT_NODE_IP=127.0.0.1). Inside that container, 127.0.0.1 is the container itself, so
    the media connection always fails. The mechanism is proven from logs. A fix has NOT been tried.

11. WHY THE CLOUD RECORDINGS FAILED WITH "Start signal not received"
==========================================================================================
SHORT ANSWER
LiveKit tells every client to send media to the address in LIVEKIT_NODE_IP. On this PC that is 127.0.0.1. The egress
recorder runs inside its own Docker container, where 127.0.0.1 means that container, not LiveKit. Its media connection
fails, so it never receives any track and never signals that recording can start.

Your normal users are not affected, because their browsers run on the PC itself, where 127.0.0.1 reaches LiveKit's
published ports.

EVIDENCE, IN ORDER (one failed recording, EG_o96azSrb6Uxt, 2026-11-04) [RUN]
  16:19:38.07  LiveKit API: StartRoomCompositeEgress, status 200. So the backend request is correct.
  16:19:39.08  LiveKit: "starting RTC session", participant EG_o96azSrb6Uxt, kind EGRESS.
               So the recorder's Chrome started and signalling to ws://livekit:7880 WORKS.
  (ICE)        LiveKit's local candidates: udp4 host 127.0.0.1:51097 and tcp4 host 127.0.0.1:7881.
               ICE check result: "state": "failed", "requestsSent": 8, "responsesReceived": 0.
  16:19:54.10  LiveKit: "participant closing", reason SIGNAL_SOURCE_CLOSE, then "removing participant without
               connection", connectionType "unknown".
  16:19:54.11  Egress: chrome: END_RECORDING
  16:19:54.16  Egress: egress_aborted, error "Start signal not received", code 412, "End reason: Source closed".

Across the logs still available [RUN]:
  - 61 egress requests, 61 "Start signal not received", 61 END_RECORDING.
  - 0 START_RECORDING.
  - 61 of 61 recorder participants ended "without connection".
  - Most ended 15-20 s after the request (51 of 61). This matches the 15 s media connection timeout: 15.02 s from the session
    start to closing in the example above.

The recorder's own template explains the error message [LIB, read from the egress v1.15.0 image]:
  - It logs START_RECORDING only after it has at least one subscribed track, which needs a working media connection.
  - It logs END_RECORDING on RoomEvent.Disconnected.
  So with no media connection, it can only end. It disconnects, END_RECORDING is logged with no START_RECORDING before
  it, and egress reports "Start signal not received".

Configuration behind it [CODE/RUN]:
  - .env: LIVEKIT_NODE_IP=127.0.0.1, LIVEKIT_USE_EXTERNAL_IP not set to true.
  - docker-compose.yml lines 155-156: use_external_ip and node_ip come from those values. The comment there already says
    127.0.0.1 only works on this PC.
  - docker-compose.yml line 205: egress ws_url ws://livekit:7880 (container network, so signalling works).
  - Signalling and media use different addresses. This is why the failure is confusing: the connection starts and then dies.

RULED OUT [RUN]
  - Backend request format: LiveKit returned 200.
  - Chrome failing to launch: the recorder's browser started and connected to LiveKit.
  - Egress out of CPU or memory: limits detected, 4 CPU; peak use about 1.5 CPU and 1.4 GB in the example. One "high cpu"
    warning in all logs.
  - Storage (MinIO): the failure happens before any file is written.
  - The silent-recording change: the failures began before that change.

WHAT IS NOT PROVEN
  [INFER]      The root cause. The mechanism is directly shown by logs, but the decisive test, a recording that succeeds
               once the address is reachable, has NOT been run.
  [UNVERIFIED] The other 20 of the 81. Their egress logs are gone (the container was recreated). All 81 rows have the same
               failure reason in the database, so the same cause is likely.
  [INFER]      10 of the 61 ended in under 15 s. These probably ended because the meeting closed first. Not checked one by
               one.
  [UNVERIFIED] Whether a later step would also fail once this one is fixed (for example upload to MinIO, or running with the
               SYS_ADMIN capability). Nothing after this step has ever run.

WHAT THIS MEANS FOR AWS
  [INFER] On EC2, LIVEKIT_NODE_IP will be the public Elastic IP, not 127.0.0.1, so this exact failure should not occur, as

12. HOW AUDIO PROCESSING AND NOISE SUPPRESSION ARE CONFIGURED
==========================================================================================
Audio passes through these stages, in this order:

  Stage 1, browser capture [CODE/LIB]
    echoCancellation: true, noiseSuppression: true (MeetingRoomPage.tsx 343; PreJoin.tsx 188 for the preview).
    autoGainControl: true comes from the livekit-client default, not your code (line 15395).

  Stage 2, Meetly noise filter [CODE] W/lib/audio/noiseFilter.ts, class NoiseFilterProcessor (97)
    A LiveKit track processor running in the browser at 48 kHz:
      80 Hz high-pass (BiquadFilterNode, LOW_CUT_HZ) -> RNNoise (AudioWorklet + WebAssembly, SIMD build when supported)
      -> limiter (DynamicsCompressorNode, threshold -2, ratio 20) -> output track.
    The chain is mono from the first node. This fixed a 6 dB loss.
    Timeouts: RESUME_TIMEOUT_MS 1500, START_TIMEOUT_MS 8000.

  Stage 3, control [CODE]
    W/pages/room/useNoiseFilter.ts: syncNoiseFilter (42) applies the processor to the microphone track, now and on each
    later publish. Called for the stage room and the own audience room (RoomView.tsx 608-609).
    W/lib/audio/noiseReductionPref.ts: on by default, saved in localStorage key mp-noise-reduction. Toggle in the
    microphone menu (NoiseReductionItem in ControlBar.tsx).

  Fallbacks [CODE]
    isNoiseFilterSupported() false: filter not used. AudioBlockedError: retried on the next click or key press. Other
    failure: plain microphone with browser processing. The microphone is never blocked by the filter.

  What receives cleaned audio [CODE, from the comment in noiseFilter.ts; INFER for cloud recording]
    The meeting and the SFU's speaking detection (they receive the published track). Speaking clips: useSpeechRecorder takes
    mic.track.mediaStreamTrack, which is the processed track. Cloud recording has never run, so that part is unconfirmed.

  CSP [CODE] web/nginx.conf line 98: script-src includes 'wasm-unsafe-eval' for WebAssembly; worker-src allows blob:.

[RUN] Noise-only test: QA found 0 clips with noise reduction on and off, because LiveKit never reported the noise as
      speaking in that test.
[UNVERIFIED] Audio quality on real microphones and in real rooms, and in Safari or Firefox. Tests used Chromium with fake
             audio devices.
