RECORDING FILTER FIX - MEETING-WISE PARTICIPANT FILTERING
================================================================================
Date    : 2026-11-02
Page    : Recordings -> "Speaking clips" (web/src/pages/recordings/SpeakingClips.tsx)
Status  : Implemented as approved, tested, independent QA done.
          QA findings (section 8) are reported only. None were fixed (awaiting approval).
Scope   : Targeted fix. Participant options stay clip-based (approved): only
          participants with speaking clips in the selected meeting are offered;
          people who joined but never produced a clip are not shown.


--------------------------------------------------------------------------------
1. ROOT CAUSE
--------------------------------------------------------------------------------
Only the dropdown options were wrong. The clip list was already filtered correctly
(GET /api/v1/speech-recordings applies meetingId AND participantId).

a) Backend dropped the relationship. GET /api/v1/speech-recordings/facets built
   the participant options with
     select distinct r.participantId, r.participantName ... where hostId/participantUserId = :user
   so no option said which meeting it belonged to.
b) The frontend never linked the two dropdowns. SpeakingClips.tsx loaded facets
   once per view and always rendered facets.participants in full, whatever
   meeting was selected.
c) No reset on meeting change. The meeting dropdown used the generic filter()
   handler, so a participant chosen for meeting A was still sent with meeting B
   (meetingId=B&participantId=<A's participation>), which silently gave an
   empty list.
(Also: a failed facets request was silently ignored; the dropdowns showed only
"All ...".)


--------------------------------------------------------------------------------
2. DATABASE RELATIONSHIP USED (no schema change)
--------------------------------------------------------------------------------
  speech_recordings.participant_id  ->  meeting_participants.id
  meeting_participants.meeting_id   ->  meetings.id     (NOT NULL)
  speech_recordings.meeting_id      ->  meetings.id     (stored on every clip)

A meeting_participants row is one person's participation in exactly ONE
meeting. The same person in two meetings has two rows and two participant ids.
Each clip's (participant_id, meeting_id) pair is therefore the real
participation relationship. Participant options come from speech_recordings
(clip-based, as approved) and carry that meeting_id. Users are never listed
as participants.

--------------------------------------------------------------------------------
5. FRONTEND CHANGES (SpeakingClips.tsx)
--------------------------------------------------------------------------------
- Participant options = all participants for "All meetings"; otherwise only those
  with meetingId === the selected meeting (useMemo over data already loaded).
  No extra API call, so the update is instant and there are no out-of-order
  responses.
- Meeting change (changeMeeting): clears the selected participant if it is not a
  participation in the new meeting, and resets to page 0. Going back to "All
  meetings" keeps it.
- Loading: the participant select is disabled with "Loading participants…".
- Empty: a meeting with no participant options shows a disabled "No
  participants in this meeting".
- Error: role="alert" message "The filter options could not be loaded: ..." with
  a Retry button.
- Date filter, view switch (resets everything), pagination, list, player and
  download are unchanged.

8. INDEPENDENT QA FINDINGS (separate QA agent; NOT fixed - awaiting approval)
--------------------------------------------------------------------------------
Verdict: the QA agent could not break the fix. No HIGH or MEDIUM findings, and
no regression in scope. It re-ran: image build (tsc + vite build), ESLint, the
recordings tests (12/12), the full web suite (199/199) and the targeted backend
tests (Facets 3/3, SpeechRecordingIntegration 6/6).

CONFIRMED
QA-1 LOW (new code). If a background facets refetch fails after the options
     have loaded (TanStack Query keeps the data and sets isError), the alert says
     "The filter options could not be loaded" while the options are still shown
     and usable. Reproduced by the agent. Possible fix: show the alert only when
     there is no data (isError && !data), or soften the wording.
QA-2 LOW / latent. The reset runs only on meeting change. If a refetch ever
     dropped the selected participant, the select would read "All participants"
     while the request still sent that participantId. The agent found no path
     that triggers this today (clips are never deleted, so facets only grow).
QA-3 INFO, existed before the fix (out of scope). A meeting renamed while it is
     live shows twice in the meeting list (each clip keeps the title it was
     recorded under), and React logs a duplicate-key warning. Participant
     filtering under either entry is still correct.
QA-4 INFO, existed before the fix (out of scope). Under "All meetings", the same
     name in two meetings appears twice ("Vicky", "Vicky"); they are different
     participations and behave correctly. Showing the meeting title in the label
     would be an optional UX change.
QA-5 INFO. If facets fail on first load, the selects stay enabled with only
     "All ..."; the alert with Retry is shown. Acceptable.

SUSPECTED (reasoned, not reproduced), existed before / out of scope
QA-6 INFO. Meeting and participant options ignore the date filter; a
     combination with no clips on that date gives an empty list (never wrong
     results).
QA-7 INFO. Options include participants whose clips are RECORDING/FAILED,
     consistent with the list, which shows those clips with a status badge.

Held up under QA: all the meeting-switch scenarios, refetch adding a
participant, page reset on meeting change, view switch with filters set
(loading state, cleared filters, cached view), no extra requests, accessibility
(labels, disabled state, role=alert + Retry), backend authorization (same rule
as the list; no leak path found; "mine" scoped to the user), NOT NULL columns
(no null meetingId, safe sort), backward-compatible response.
QA note: no test checks that an unrelated user gets empty facets (the query
makes a leak impossible; it would only guard against regressions).
