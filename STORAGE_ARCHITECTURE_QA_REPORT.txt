F1  HIGH  CONFIRMED DEFECT  FAIL
Title: A person removed from a meeting can still delete shared files
Code:  B/file/service/FileService.java:178-189 (delete calls participantAccess.resolve, line 179)
       B/participant/service/ParticipantAccessService.java:57-67 (resolve checks identity only, not state)
       B/participant/service/ParticipantAccessService.java:71-78 (resolvePresent, used by upload)
       B/participant/entity/MeetingParticipant.java:176-180 (remove keeps the role)
       B/moderation/service/ModerationService.java:261
What goes wrong: resolve proves who the caller is, never whether they may still act. remove() changes the state but not
the role, so a kicked co-host stays a moderator for this check, for good, and can erase every shared file in the
meeting. Deletion is unrecoverable. It also works after the meeting has ended, and a guest's token stays valid because
nothing rotates it on removal.
Evidence: TEST, executed by QA. A temporary class in a scratch copy (not in the project), with its own database and
mocked ObjectStorage: host promotes Bob to co-host, host removes Bob, Bob deletes Alice's file: 204, and storage.delete
was called. A removed uploader deleting their own file: 204. Printed as "QA-RESULT removed co-host DELETE status=204"
and "QA-RESULT removed uploader DELETE status=204". The project's FileDeleteIntegrationTest has no such case.

Who can do what, by the caller's state (SOURCE, except the two rows marked TEST):
  State                        Upload           List/download                     Delete
  ADMITTED, JOINED             Yes (a)          Yes                               Uploader or moderator
  LEFT                         No               Yes                               Uploader or moderator
  LEFT, meeting ended          No               Yes                               Uploader or moderator, no meeting check
  REMOVED, moderator role      No               Not as participant (b)            YES (TEST: 204). DEFECT
  REMOVED, uploader            No               Not as participant (b)            YES (TEST: 204). DEFECT
  REMOVED, neither             No               Not as participant (b)            No, 403
  DENIED                       No               Not as participant (b)            Only if uploader or moderator; in practice no (c)
  WAITING                      No               Not as participant (b)            Only if uploader or moderator; in practice no (c)
  (a) Also needs FILE_SHARE, and in a stage-only meeting a moderator role.
  (b) ParticipantAccessService.java:40-54: a participant must be wasAdmitted (ADMITTED, JOINED, LEFT). A signed-in user
      then falls through to canView: host, system admin, invited, organization member or past participant. Whether
      hasParticipated stays true for a removed user was not fully traced.
  (c) A DENIED or WAITING row has never uploaded, and a moderator is admitted straight away (JoinService.java:112-172),
      so no reachable path was found. Not executed.
So delete is looser than both upload and download: it is the only one of the three with no state check at all.

Required fix: in delete, require a state check. Suggested rule: refuse REMOVED and DENIED always, require resolvePresent
for the moderator branch, and decide explicitly whether a LEFT uploader or an ended meeting may delete. Add tests.

F4  MEDIUM  CONFIRMED DEFECT  FAIL
Title: deleteExpired: failing rows throttle, and 50 of them permanently block, clip retention
Code:  B/recording/service/SpeechRecordingService.java:289-314
       B/recording/repository/SpeechRecordingRepository.java:41-47 (order by startTime, no change on failure)
       Compare B/recording/service/RecordingService.java:380-399, which moves a failing row's retention date forward.
Evidence: SOURCE. Not executed. The tests cover all-fail and all-succeed only.
Answers to the owner's questions:
  - Infinite loop: no. The loop continues only when all 50 succeed, and each success leaves the query.
  - Does a failing row block others on the next run? Yes, partly. A failed row is not changed, so it returns at the
    front of page 0 every run. With F failing rows at the front (F below 50), the first batch deletes 50-F, n is below
    50, and the run ends. The job therefore removes at most 50-F clips a day, repeatedly.
  - Can 50 failing rows starve everything behind them permanently? Yes. n=0 every run, and no later row is ever reached
    while those 50 keep failing.
  - One transient failure also ends that night's run after the current batch. The next run catches up, so this is only
    a day's delay.
  - Scale: this database took 128, 207 and 137 clips on 2026-11-02 to 04 (REAL, SELECT; test traffic). One stuck row
    means a cap of 49 a day, below that rate, so the backlog would grow.
  - What makes a row fail persistently: not a vanished object (delete of a missing key succeeds). Realistic cause: keys
    outside the IAM policy, such as old rows after AWS_S3_PREFIX changes. That gives 403 on every delete, and could be
    well over 50 rows, which is the permanent case.
  - Effect: objects are still removed by the lifecycle rule, but rows stay listed past retention, and playback answers
    "no longer available". No data is lost.
  - Alerting: one log.warn per failed row per run with the clip id ("retrying next run"). No metric, no alert, no health
    signal, no failure count. The success line is INFO and only when n>0.
Required fix: follow RecordingService, or use keyset paging past failed rows, or record attempts, and add a failure
count log plus a metric.

F8  MEDIUM  POTENTIAL RISK  NEEDS VERIFICATION
Title: S3 calls run inside open database transactions
Code:  B/recording/service/SpeechRecordingService.java:229-254 (finish holds a row lock during upload), :289-314
       B/common/storage/S3Operations.java:35-36 (10 s connect, 2 min transfer)
       application.yml hikari maximum-pool-size 20; no scheduler pool setting found, so one scheduler thread (Spring default)
What goes wrong: a slow S3 holds a connection and row lock per clip finish for up to minutes. In a meeting with many
speakers this could use up the pool of 20 and stall unrelated requests. A retention batch can hold one connection for
50 S3 calls, and in a hang could exceed the 30-minute job lock and delay every other scheduled job. Repeat runs are
safe, because delete is idempotent.
No retry exists in S3Operations. Clip uploads are retried by the recovery job, but a clip that finished fully then
ends INCOMPLETE, not COMPLETED.
Evidence: SOURCE. Not executed.
Required fix: upload outside the transaction, and delete each row in its own short transaction.
