0. SUMMARY AND LAUNCH BLOCKERS
================================================================================

Frontend      React 19.1.1 + TypeScript 5.9.2, built by Vite 7.1.3, served by
              nginx 1.27 (Docker).
Backend       Spring Boot 4.0.9 on Java 21 - one modular-monolith REST API.
Database      PostgreSQL 17 (Docker image), schema managed by Flyway (V1..V9).
Cache         Redis 7.4 (rate limits, job locks, room signal numbers; LiveKit).
Media         LiveKit SFU 1.13.11 (WebRTC) + LiveKit Egress 1.15.0 (recording).
Storage       S3-compatible object storage (MinIO) + a local disk folder for
              speaking clips.
Real-time     No application WebSocket server. LiveKit signalling WebSocket and
              LiveKit data channel carry all real-time updates.
Deployment    Docker Compose: 10 services + 3 optional observability services.
WebRTC model  SFU (self-hosted LiveKit). Not P2P, not MCU, not a third-party
              media provider.

BLOCKERS before a Linux production launch:
  B1. No HTTPS anywhere in the stack. Browsers only allow camera/microphone on
      HTTPS (or localhost). A TLS reverse proxy is required for the web app,
      the API and the LiveKit WebSocket.
      [EVIDENCE] docker-compose.yml (web 3000:80, livekit 7880, minio 9000),
                 web/nginx.conf (listen 80 only)
  B2. LiveKit advertises 127.0.0.1 for media by default (LIVEKIT_NODE_IP
      default 127.0.0.1, use_external_ip: false). Remote users get no
      audio/video until the server's public IP is set.
      [EVIDENCE] docker-compose.yml service livekit (LIVEKIT_CONFIG)
  B3. Windows paths are the defaults: DATA_ROOT defaults to D:/meetly/docker.
      On Linux set it to e.g. /srv/meetly.
      [EVIDENCE] docker-compose.yml (6 bind mounts), .env.example
  B4. The production Spring profile is never activated: Compose does not pass
      SPRING_PROFILES_ACTIVE, and .env.example holds development values
      (APP_COOKIE_SECURE=false, APP_OPENAPI_ENABLED=true, SMTP_HOST=mailpit).
      [EVIDENCE] docker-compose.yml service backend, .env.example,
                 backend/src/main/resources/application-prod.yml
  B5. No TURN server configured. Users behind strict firewalls will fail to
      connect media.
      [EVIDENCE] docker-compose.yml (no "turn:" block), docs/07-deployment.md

    |                                              -> MinIO bucket

  [EVIDENCE] docker-compose.yml, web/nginx.conf, docs/02-architecture.md,

4.1 Frontend architecture

    (web/dist) and served by nginx.
  - React Router 7 for pages; TanStack Query for server data; react-hook-form
    + zod for forms; Radix UI primitives + Tailwind CSS 4 for UI.
  - Layout: web/src/pages/ (dashboard, meetings, room, recordings, scheduling,
    settings, admin, auth, public booking), web/src/lib/api/ (REST client and
    endpoint definitions), web/src/lib/auth/, web/src/lib/recorder/,

  - API base URL baked in at build time (VITE_API_BASE_URL, default /api/v1,

    /login/oauth2/, /swagger-ui, /v3/api-docs to the API.
  [EVIDENCE] web/package.json, web/vite.config.ts, web/Dockerfile, web/src/

4.2 Backend architecture
  - One Spring Boot application ("modular monolith", 194 Java source files).
    Feature modules under .../ : administration, analytics, booking, calendar,
    chat, common, dashboard, file, identity, media, meeting, moderation,
    notification, organization, participant, recording, room, scheduling.
    Each module has controller / service / repository / entity layers.
  - REST + JSON with RFC 7807 problem details; Java 21 virtual threads on;
    graceful shutdown; Tomcat max 200 threads; multipart limit 25 MB.
  - Scheduled jobs (notification dispatch, recording reconciliation,
    speaking-clip recovery) are serialised across instances with a Redis lock.
  - Health: /actuator/health/liveness, /actuator/health/readiness (db + redis).
    Metrics: /actuator/prometheus behind HTTP Basic

4.4 Authentication flow
  1. Register with e-mail + password; e-mail verification required by default.
     Optional Google/Microsoft sign-in with the "oauth" profile; the proxy must
     route /oauth2/ and /login/oauth2/ to the backend.
  2. Login -> access token (JWT HS256, 15 min) used as
     "Authorization: Bearer <token>".
  3. Refresh token (opaque, 30 days) in a SameSite=Strict, Secure cookie
     scoped to /api/v1/auth; /auth/refresh and /auth/logout also require the
     X-Requested-With header (CSRF protection without tokens).
  4. Brute-force protection: 10 failures -> 15 min lockout; per-client failure
     tracking; Redis-backed rate limits.
  5. Authorization: /api/v1/admin/** requires SYSTEM_ADMIN; an explicit list of
     anonymous routes (meeting join, public booking, webhooks, signed file
     URLs); everything else requires a valid JWT. Guests use
     X-Participant-Token, checked inside the services.
  [EVIDENCE] .../common/security/SecurityConfig.java,
             .../common/security/JwtService.java, application.yml app.auth /
             app.security, application-oauth.yml,
             db/migration/V5__login_failures_per_client.sql

4.5 Meeting creation and joining flow
  1. A signed-in host creates a meeting (scheduled, instant or personal room)
     through the REST API and receives a join code and link (/j/<code>).
  2. A participant opens the link; the meeting is looked up by code
     (GET /api/v1/meetings/by-code/*, public). Guests enter a name.
  3. POST /api/v1/meetings/{id}/join enforces waiting room, lock, password
     and capacity (default 100, hard max 300).
  4. On admission the API returns a LiveKit access token (TTL 10 min) and the
     LiveKit WebSocket URL (LIVEKIT_PUBLIC_URL).
  5. The browser connects with <LiveKitRoom>. LiveKit reports joins/leaves to
     the API through signed webhooks; the API stores presence and history.
  6. "Host and self only" (webinar-style) meetings put each attendee in an
     audience room of their own; moderators get extra tokens via
     GET /api/v1/meetings/{id}/audience-access.
  [EVIDENCE] docs/04-api-contracts.md, .../common/security/SecurityConfig.java,
             .../media/service/MediaService.java,
             .../media/webhook/LiveKitWebhookController.java,
             web/src/pages/room/JoinFlow.tsx,
             web/src/pages/room/MeetingRoomPage.tsx,
             web/src/pages/room/useAudienceRoom.ts,
             application.yml app.livekit, app.meetings

4.6 Real-time communication architecture
  - No application WebSocket server.
  - Server -> clients: LiveKit data channel. Only the server publishes (through
    the LiveKit server API) on the topics chat, moderation, recording, files,
    hand, reactions, presence. Messages carry sequence numbers so clients
    detect gaps and reload room state. Delivery is best-effort and happens
    after the database transaction commits.
  - Clients -> server: REST calls (chat messages, raise hand, reactions).
  [EVIDENCE] .../media/service/RoomSignals.java, backend/pom.xml (no websocket
             starter), .../common/security/SecurityConfig.java

4.7 Audio/video transmission architecture
  VERDICT: SFU (self-hosted LiveKit). Not peer-to-peer, not MCU, not a
  third-party media provider.
  - Each browser publishes its tracks once to the LiveKit SFU, which forwards
    them to the other participants. Media never passes through the API.
  - Signalling: WebSocket to LiveKit port 7880 (ws:// in compose; must be
    wss:// in production).
  - Media: UDP 50000-50100; TCP fallback 7881; no TURN configured.
  - Voice-activity detection ("who is speaking") is done by LiveKit with the
    "audio:" settings (active_level 35, min_percentile 40,
    update_interval 400 ms, smooth_intervals 2).
  [EVIDENCE] docker-compose.yml service livekit; docs/02-architecture.md
             (line 22 "LK[LiveKit SFU]", line 53 "Browsers exchange media with
             the SFU"); loadtest/run-media-load.sh ("against the SFU");
             web/package.json (livekit-client 2.15.5)

4.8 Recording architecture (three independent kinds)
  a) Whole-meeting (composite) "cloud" recording
     The API asks LiveKit to start an Egress job; Egress renders the room in
     headless Chrome and uploads an MP4 to the S3 bucket S3_RECORDINGS_BUCKET
     at recordings/<meetingId>/<recordingId>.mp4. Can start automatically
     ("Record automatically"). Retention: 90 days by default.
     [EVIDENCE] docker-compose.yml services egress, minio;
                .../recording/service/RecordingService.java,
                .../recording/service/AutoRecordingService.java;
                application.yml app.recording
     NOTE: on the development PC every composite recording failed ("The media
     server is unavailable") because no Egress worker runs there. This path
     is NOT verified end to end.
  b) Speaking clips
     Each participant's browser records its own microphone (+camera when on)
     per speaking turn with MediaRecorder and uploads 1-second chunks. The
     server names, writes (.part), verifies (WebM/EBML header) and finalises
     each file under
       RECORDING_STORAGE_PATH/DD-MM-YYYY/<Meeting_Title>/<Participant_Name>/
         DDMMYYHHmmss_<6 hex>.webm
     Files are served through 10-minute HMAC-signed URLs after an access
     check; access is audited. A recovery job closes abandoned clips.
     [EVIDENCE] web/src/pages/room/useSpeechRecorder.ts,
                .../recording/service/SpeechRecordingService.java,
                .../recording/service/SpeechClipStorage.java,
                db/migration/V9__speech_recordings.sql
  c) Local recording
     The user records the meeting tab with getDisplayMedia + MediaRecorder;
     the file is downloaded to their own device. The API only records that it
     started (POST /api/v1/meetings/*/local-recordings).
     [EVIDENCE] web/src/lib/recorder/localRecorder.ts,
                .../common/security/SecurityConfig.java

4.9 File storage architecture
  - Meeting file sharing: uploads up to 25 MB; allow-listed types (PDF, PNG,
    JPEG, GIF, WebP, text, CSV, DOCX, XLSX, PPTX, ZIP); stored in S3 bucket
    S3_FILES_BUCKET (default meet-files); downloads by presigned URL valid
    15 min built with S3_PUBLIC_ENDPOINT.
  - The API creates the buckets at startup.
  - Dev profile only: APP_STORAGE_TYPE=local keeps the buckets on disk
    (D:/meetly) and serves them via /api/v1/storage/local with an HMAC
    signature.
  [EVIDENCE] application.yml (app.files, app.storage), application-dev.yml,
             .../common/storage/LocalFileObjectStorage.java,
             docker-compose.yml (minio comment)

9.4 Network ports
  Expose to the internet:
    443/tcp           TLS reverse proxy (web, API, LiveKit wss, S3 endpoint)
    80/tcp            HTTP -> HTTPS redirect, ACME challenges
    7881/tcp          LiveKit WebRTC over TCP (fallback)

9.5 Firewall requirements
  Allow inbound 80, 443, 7881/tcp, 50000-50100/udp (+ TURN ports if
  enabled); deny all other inbound. NOTE: Docker-published ports bypass ufw
  rules by default - bind 3000, 7880, 9000 to 127.0.0.1 or filter in the
  DOCKER-USER iptables chain.

9.6 SSL requirements
  Certificates for the app domain (e.g. meet.example.com) and the media
  domain (e.g. media.example.com), plus the TURN domain if used. HTTPS is
  mandatory for camera/microphone and for the Secure refresh cookie.

9.7 Reverse proxy requirements
  - Route /api/*, /oauth2/*, /login/oauth2/* to the API (or to the web
    nginx, which already proxies them).
  - Route the media host to LiveKit :7880 with WebSocket upgrade.
  - Forward Host, X-Forwarded-For, X-Forwarded-Proto, X-Forwarded-Host
    (API uses server.forward-headers-strategy=native).
  - Block /actuator/* from the internet.
  - Allow request bodies >= 30 MB (files 25 MB; clip chunks 8 MiB).
  [EVIDENCE] docs/07-deployment.md, web/nginx.conf, application.yml

9.8 Recording storage requirements
  - Dedicated disk/volume for ${DATA_ROOT}.
  - Composite MP4s in MinIO (${DATA_ROOT}/minio); retention 90 days.
  - Speaking clips in ${DATA_ROOT}/Recordings: up to 500 MiB per clip, 8 MiB
    per chunk; new clips refused below 200 MiB free. No automatic deletion
    of speaking clips was found.
  - The folder must be writable by the container user "app" (non-root).
  [EVIDENCE] application.yml app.speech-recordings, app.recording,
             backend/Dockerfile (USER app)

9.9 Database persistence requirements
  - Named volume pgdata under /var/lib/docker/volumes: size that filesystem
    or move Docker's data root.
  - Never run "docker compose down -v" (deletes volumes).

9.10 Backup requirements
  - Nightly pg_dump exists but stays on the same host
    (${DATA_ROOT}/backups, 14 days).
  - Copy ${DATA_ROOT}/backups, ${DATA_ROOT}/minio and ${DATA_ROOT}/Recordings
    off the server; test restores.
  - docs recommend WAL archiving (pgBackRest/WAL-G) for point-in-time
    recovery and bucket versioning/replication for object storage.
  - Secrets in a secret manager with versioning.
  [EVIDENCE] docker-compose.yml pg-backup, docs/07-deployment.md
             "Backup and restore"

10. SECURITY AND PRODUCTION RISKS
================================================================================
Ordered by severity. "Open QA" = finding from the independent QA review of
speaking-clip recording (31 Oct 2026), known and not yet fixed.

[CRITICAL] R1 Missing TLS
  Web (3000), LiveKit (7880, ws://) and MinIO (9000) are plain HTTP. Camera/
  mic are blocked on non-HTTPS origins; refresh cookies are Secure.
  [EVIDENCE] docker-compose.yml, web/nginx.conf

[CRITICAL] R2 Media reachability
  LiveKit node_ip defaults to 127.0.0.1, use_external_ip false.
  [EVIDENCE] docker-compose.yml livekit, .env.example LIVEKIT_NODE_IP

[CRITICAL] R3 Linux compatibility - Windows default paths
  DATA_ROOT defaults to D:/meetly/docker for 6 bind mounts.
  [EVIDENCE] docker-compose.yml, .env.example

[HIGH] R4 Development-only configuration
  SPRING_PROFILES_ACTIVE is not passed by compose, so application-prod.yml
  never applies. .env.example uses APP_COOKIE_SECURE=false,
  APP_OPENAPI_ENABLED=true, OTEL_SAMPLING_PROBABILITY=1.0, SMTP_HOST=mailpit,
  localhost URLs.
  [EVIDENCE] docker-compose.yml backend env, .env.example,
             application-prod.yml

[HIGH] R5 Missing environment variables in compose
  GOOGLE_CLIENT_ID/SECRET, MICROSOFT_CLIENT_ID/SECRET, MICROSOFT_TENANT and
  S3_FILES_BUCKET are not passed to the backend container; social sign-in
  cannot work in Docker even when set in .env.
  [EVIDENCE] docker-compose.yml vs application-oauth.yml, application.yml

[HIGH] R6 No TURN server
  Users behind restrictive firewalls/proxies cannot connect media.
  [EVIDENCE] docker-compose.yml, docs/07-deployment.md

[HIGH] R7 Open QA RC-3 - database pool exhaustion
  A participant can hold DB connections while slowly uploading clip chunks.
  [EVIDENCE] .../recording/service/SpeechRecordingService.java appendChunk

[HIGH] R8 Incomplete backups
  Recordings, shared files and speaking clips are not backed up; DB dumps
  stay on the same host.  [EVIDENCE] docker-compose.yml pg-backup

[MEDIUM] R9 Unprotected ports
  3000, 7880, 9000 (and 7881 + UDP range, which must be public) are
  published on all interfaces; Docker bypasses ufw. PostgreSQL, Redis,
  pgAdmin, Mailpit and observability UIs are correctly on 127.0.0.1.
  [EVIDENCE] docker-compose.yml ports

[MEDIUM] R10 File permissions (open QA RC-13)
  Backend runs as non-root "app"; on Linux, Compose creates
  ${DATA_ROOT}/Recordings owned by root, so clip writes may fail.
  [EVIDENCE] backend/Dockerfile, docker-compose.yml create_host_path

[MEDIUM] R11 Horizontal scaling
  Speaking clips live on the API's local disk; >1 API instance needs a
  shared filesystem.
  [EVIDENCE] application.yml app.speech-recordings, SpeechClipStorage.java

[MEDIUM] R12 Open QA RC-6 / RC-7

  [EVIDENCE] local DB: every "recordings" row FAILED; docker-compose.yml
