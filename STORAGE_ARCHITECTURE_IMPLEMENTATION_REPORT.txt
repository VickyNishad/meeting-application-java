ENVIRONMENT-BASED FILE STORAGE (LOCAL DEVELOPMENT + AWS S3 PRODUCTION)
Implementation report, 5 November 2026, corrected and extended 6 November 2026 (section 9)
Status: implemented and tested locally, not verified on real AWS. Not ready for production. Nothing committed or pushed.


1. RESULT

STORAGE_PROVIDER now chooses where everything is kept.
  local   Files and recordings on disk, clips on disk. No AWS account or MinIO needed.
  s3      One private bucket with prefixes, reached through the EC2 instance role.

Compose now starts React, Java, LiveKit, PostgreSQL and Redis. MinIO and Egress start only on request
(--profile minio, --profile egress). MinIO has not been removed.

NOT TESTED AGAINST REAL SERVICES
  - No test ran against real AWS S3 or a real IAM role. S3 tests used a MinIO container.
  - No test ran against real Egress. Cloud recording is off, and tests that start it use a mocked provider.
  - The lifecycle rule and the IAM policy in docs/07-deployment.md have never been applied to a real bucket.
These must be checked on the AWS account before going live (section 7).


2. YOUR 7 CONDITIONS

1. 90-day rule on speaking clips only
   Done. The documented rule filters on the prefix speaking-clips/. The application cannot change it: its
   IAM policy has no lifecycle permission. Not yet applied to a real bucket.
2. Shared files never deleted automatically
   Done. No job or rule touches files/. A file goes only when its uploader or a host deletes it.
3. Whole-meeting recording retention separate
   Done. APP_RECORDING_RETENTION_DAYS stays separate from APP_SPEECH_CLIP_RETENTION_DAYS.
4. Database and S3 stay consistent
   PARTIAL (corrected 6 November). The object is deleted first, then the row is marked. If storage fails the row
   stays and the job retries. QA found gaps: F4 and F5 are fixed, F7 and F10 are open.
   Rows hold relative keys, so they do not depend on a server name. Migration V11 adds speech_recordings.deleted_at.
5. Expired or missing objects handled gracefully
   Done, with a limit (corrected 6 November). Files, recordings and S3 clips are checked before a link is issued and
   answer "no longer available". Local clips are not checked in advance: a missing file is reported on playback.
6. Cloud recording off by default
   Done. APP_CLOUD_RECORDING_ENABLED=false hides the control, refuses manual starts with a clear message, skips
   automatic starts, and leaves no failed rows. Speaking clips carry on.
7. MinIO not removed until migrated
   Done. MinIO stays as an optional profile, and docker/minio was not touched. The io.minio Java library stays
   by decision 1: it is the S3 client, used only in S3Operations.java and pom.xml.


3. WHAT CHANGED

Backend
  - S3Operations.java (new): the one place that talks to S3, on AWS or a compatible server.
    Empty keys use the IAM role. A custom endpoint without keys stops at startup.
  - MinioObjectStorage renamed to S3ObjectStorage. On AWS it never creates or changes a bucket.
  - LocalFileObjectStorage: folders are now shared-files and meeting-recordings; one bucket name for both works.
  - ObjectStorage gained exists().
  - Speaking clips: retention job at 03:45, S3 only, 50 at a time. Local clips are never removed.
  - New endpoint: DELETE /api/v1/meetings/{id}/files/{fileId}, for the uploader or a moderator.

Frontend
  - Delete button with confirmation in Chat > Files, for the uploader and moderators.
  - Cloud recording section hidden in Host controls when the server has no recorder.

Configuration and docs
  - docker-compose.yml, .env.example, .gitignore (/storage/), README-Docker.md, docs/06-security.md and
    docs/07-deployment.md (bucket setup, IAM policy, lifecycle rule, instance metadata hop limit 2, Egress).

Security rules
  - No keys in code or Git. A scan of the diff for AWS keys and private keys found nothing.
  - Browsers only get short-lived signed links, issued after the API has checked access.
  - Local development works with no AWS credentials.


4. DIFFERENCES FROM THE APPROVED PLAN

Simpler than planned
  - ObjectStorage keeps its bucket parameters rather than moving to logical areas. A HashMap and one-bucket
    keys fix the crash with far less change.
  - Clips keep SpeechClipObjectStore on top of S3Operations, because their mode is set separately and the
    existing S3 tests rely on it.
  - LiveKitMediaAdapter and the Caddyfile did not change.

Added, not in the plan (please review)
  - prod now refuses to start with STORAGE_PROVIDER=local. Without this, Compose's default would have sent
    files to a MinIO that is not running and kept clips on disk, failing only at the first upload.
  - .env.example now defaults to the development setup: SPRING_PROFILES_ACTIVE= (empty) and STORAGE_PROVIDER=local.
    The old prod value would now stop at startup, and it also forced Secure cookies on plain HTTP.
  - S3_ACCESS_KEY and S3_SECRET_KEY are empty in the example, because AWS uses the role.

    inside your 51000-51100 range. I used LIVEKIT_RTC_PORT_START=53000 and LIVEKIT_RTC_PORT_END=53100 as

Design decisions
  F1  Standing is checked across all of a signed-in user's rows. A new session makes a new row, so a person removed
      on one row could otherwise have used an older LEFT row. A removed person gets the
      same 403 whether or not the file exists.
  F2  prod with an S3-compatible server is still possible for files, but clips only go to AWS S3.
  F4  Paging by position (start time, then id) needs no migration, so no schema changed. A failed clip is simply
      tried again on the next nightly run. There is no backoff and no stored failure count.
      One run stops after 20 minutes, below its 30-minute lock, so an outage cannot run past the lock.
  F6  Found during this work: application.yml defaulted S3_PUBLIC_ENDPOINT to http://localhost:9000 outside Compose.
      The default is now empty. On AWS, S3_FILES_BUCKET and S3_RECORDINGS_BUCKET must match AWS_S3_BUCKET.
