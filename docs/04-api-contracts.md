# 04 — API Contracts (v1)

All endpoints live under `/api/v1`. The machine-readable contract is generated by springdoc at
`/v3/api-docs` (JSON) and rendered at `/swagger-ui.html` when the backend runs. This document is the
human-readable source of truth that the generated spec must match.

## Conventions

| Topic | Rule |
|---|---|
| Format | JSON, UTF-8. Field names are `camelCase`. |
| Ids | UUID strings. |
| Instants | ISO-8601 UTC (`2026-10-27T09:30:00Z`). |
| Local dates/times | `YYYY-MM-DD`, `HH:mm`. Always accompanied by an IANA `timeZone`. |
| Auth | `Authorization: Bearer <accessToken>` (JWT, 15 min). Refresh token in HttpOnly cookie `mp_refresh` (`Path=/api/v1/auth`, `SameSite=Strict`, `Secure` in prod) **or** in the request body for native clients. |
| CSRF | Cookie-authenticated endpoints (`/auth/refresh`, `/auth/logout`) require header `X-Requested-With: XMLHttpRequest`. Bearer-authenticated endpoints are not cookie-authenticated and are therefore not CSRF-exposed. |
| Pagination | `?page=0&size=20` (max 100). Response: `{ "items": [], "page": 0, "size": 20, "totalItems": 0, "totalPages": 0 }`. |
| Idempotency | `POST /bookings` and `POST /meetings` accept optional `Idempotency-Key` header (8–64 URL-safe chars). The key is reserved before the request runs, so concurrent duplicates never both execute: while the first is still running, a duplicate gets `409 IDEMPOTENCY_IN_PROGRESS` (retry shortly); afterwards, replays within 24 h return the original response with header `Idempotent-Replayed: true`. The same key with a different body → `409 CONFLICT`. A request that fails releases its key. |
| Optimistic locking | Mutable resources return `version`; `PATCH` bodies may include `version`. Mismatch → `409 OPTIMISTIC_LOCK_CONFLICT`. |
| Rate limiting | Per-IP and per-user token buckets (Redis). Exceeded → `429 RATE_LIMITED` with `Retry-After`. |

### Shared DTOs

```ts
type UserSummary  = { id: string; displayName: string; email: string | null /* null where the viewer may not see it,
                       e.g. Meeting.host inside JoinResponse */; avatarUrl?: string };
type UserProfile  = UserSummary & { timeZone: string; emailVerified: boolean; systemRole: "SYSTEM_ADMIN" | "USER";
                                     status: "ACTIVE" | "DISABLED"; createdAt: string };
type AuthResponse = { accessToken: string; tokenType: "Bearer"; expiresIn: number; refreshToken?: string /* native clients only */;
                      user: UserProfile };

type MeetingType    = "INSTANT" | "SCHEDULED" | "PERSONAL_ROOM" | "ONE_TO_ONE";
type MeetingStatus  = "SCHEDULED" | "LIVE" | "ENDED" | "CANCELLED";
type MediaMode      = "VIDEO" | "AUDIO_ONLY";
type Privacy        = "LINK" /* anyone with link */ | "ORGANIZATION" | "INVITEES_ONLY";
type MeetingRole    = "HOST" | "CO_HOST" | "PARTICIPANT" | "GUEST";
type ScreenSharePolicy = "EVERYONE" | "HOSTS_ONLY";

type Meeting = {
  id: string; joinCode: string; joinUrl: string; title: string; description?: string;
  type: MeetingType; status: MeetingStatus; mediaMode: MediaMode; privacy: Privacy;
  organizationId?: string; host: UserSummary;
  startTime?: string; endTime?: string; timeZone: string; recurrenceRule?: string /* RFC 5545 RRULE */;
  passwordProtected: boolean; waitingRoomEnabled: boolean; allowGuests: boolean; joinBeforeHost: boolean;
  muteOnEntry: boolean; maxParticipants: number; screenSharePolicy: ScreenSharePolicy; locked: boolean;
  myRole?: MeetingRole; createdAt: string; version: number;
  autoRecord: boolean /* record the room and each participant automatically (see Recordings) */;
  recordingInProgress: boolean /* a recording of the live session is running now; join pages and rooms must say so */;
};
```

```ts
type CreateMeetingRequest = {
  title: string /* 1..200 */; description?: string /* ≤ 5000 */;
  type: "INSTANT" | "SCHEDULED" | "ONE_TO_ONE"; mediaMode?: MediaMode /* VIDEO */; privacy?: Privacy /* LINK */;
  organizationId?: string; startTime?: string /* required for SCHEDULED, future */; durationMinutes?: number /* 5..1440, default 60 */;
  timeZone: string; recurrenceRule?: string; password?: string /* 4..64 */;
  waitingRoomEnabled?: boolean; allowGuests?: boolean; joinBeforeHost?: boolean; muteOnEntry?: boolean;
  maxParticipants?: number /* 2..300, ONE_TO_ONE forces 2 */; screenSharePolicy?: ScreenSharePolicy;
  inviteeEmails?: string[] /* ≤ 300 */; autoRecord?: boolean /* default false; also accepted by PATCH */;
};

type JoinResponse = {
  status: "ADMITTED" | "WAITING" | "DENIED";
  participantId: string;
  waitToken: string /* participant secret, returned on every join. Used for join-status polling and, for guests,
                       as X-Participant-Token on leave/chat/files/local-recordings. Keep in memory/sessionStorage only. */;
  role: MeetingRole;
  livekitUrl?: string; token?: string /* LiveKit JWT, TTL ≤ 10 min, only when ADMITTED */;
  roomName?: string; meeting: Meeting /* meeting.host.email is always null here (callers may be anonymous guests) */;
};

type ParticipantView = {
  id: string; userId?: string; displayName: string; role: MeetingRole;
  state: "WAITING" | "ADMITTED" /* token issued, not yet connected */ | "JOINED" | "LEFT" | "REMOVED" | "DENIED"; joinedAt?: string; leftAt?: string; durationSeconds?: number;
};
```

Join rules evaluated by the server in this order: meeting exists → not CANCELLED/ENDED → caller allowed by `privacy` (invitee / org member / link) → guests allowed if anonymous → password (`MEETING_PASSWORD_REQUIRED` / `MEETING_PASSWORD_INVALID`) → room not locked (hosts/co-hosts bypass) → capacity (`MEETING_FULL`; hosts and co-hosts are exempt, but still take a seat) → waiting room (hosts/co-hosts and invitees-by-account bypass when configured) → issue token. The media room is only created once all these checks have passed.

`CO_HOST` is scoped to one live session: it is kept when the co-host re-joins the same session, but never carried into a later
session of the meeting (or personal room), and a removed participant loses it. When a session starts, people waiting for the host
are admitted earliest first up to `maxParticipants`; the rest stay `WAITING` (`waitingReason: "WAITING_ROOM"`) for a moderator to
admit. A participant who left and reconnects with a still-valid media token is ejected if the room has since been locked or filled
(moderators exempt), unless it left within `app.meetings.reconnect-window` (default 30 s: a reload, second tab or role-change
reconnect, which takes its seat and in-session role back; joining again within the window reuses the participation too);
removed participants are always ejected. A join event of a connection whose leave was already processed is ignored. The join
response `role` is the participation's current role.

LiveKit token grants: `roomJoin`, `room=<roomName>`, `canSubscribe=true`, `canPublish=true`,
`canPublishSources = [camera, microphone] (+ screen_share, screen_share_audio when allowed)`, `canPublishData=true`,
`canUpdateOwnMetadata=false`, `roomAdmin=false` (never issued to clients). Identity = `participantId`; metadata = `{"role":"HOST","userId":"…"}`.
`AUDIO_ONLY` meetings omit `camera` and screen-share sources.

(the participant is REMOVED / the role or policy is stored); repeating the same call is safe and re-applies it to the media server.

```ts
type Recording = { id: string; meetingId: string; meetingTitle: string;
  kind: "CLOUD" /* whole room */ | "PARTICIPANT" /* one person's camera + microphone */;
  status: "STARTING" | "ACTIVE" | "STOPPING" | "PROCESSING" | "AVAILABLE" | "FAILED" | "DELETED";
  startedAt?: string; endedAt?: string; durationSeconds?: number; sizeBytes?: number; failureReason?: string;
  retentionUntil?: string; startedBy?: UserSummary; autoStarted: boolean;
  participantId?: string; subjectUserId?: string /* absent for guests */; subjectName?: string };
```

**Automatic recording** (`autoRecord: true`): when the SFU confirms a participant's media connection
(`participant_joined` webhook), the server starts that participant's own recording (`kind: "PARTICIPANT"`, MP4) and,
if none is running, one room recording (`kind: "CLOUD"`, `autoStarted: true`). Each is announced on the `recording`
topic before capture and is not started (status `FAILED`) if the room cannot be notified. A reconnect does not start
a second recording while one is in flight. The host stops any of them with `POST …/recordings/{id}/stop`; a stopped
auto recording is not started again by later joins or reconnects (room: for that session; participant: for that
participant) until auto-record is switched off and on again. Switching `autoRecord` off (PATCH) stops every running
auto-started recording and announces it. Stop/failure notices on the `recording` topic carry the recording's own
`kind` (and `participantId` for a participant recording), so one person's recording stopping never reads as the room
recording stopping.

Who may view a recording: the host, org admins and system admins see all. A `PARTICIPANT` recording is otherwise
visible only to its subject when they were signed in (`subjectUserId`); guests' recordings stay with the host. An
auto-started room recording is the host's only; a moderator-started room recording is shared with everyone who was
admitted to the meeting. Anything else is `404`.

### 7.1 Speaking clips

In meetings with `autoRecord` on (everyone is told before joining), each participant's own browser records its own
microphone (and camera, if on) for every speaking turn: a turn starts when the media server reports that participant
speaking and ends after 1.5 s of silence, a mute or leaving. The browser streams the clip to the API in numbered
chunks; the server names and files it:

```
<RECORDING_STORAGE_PATH>/DD-MM-YYYY/<Meeting_Title>/<Participant_Name>/DDMMYYHHmmss_<6 hex>.webm
```

Date and time are the server's start time in the meeting's time zone. Titles and names are sanitized to one folder
name (letters, combining marks and digits of any script, `-`, `_`; spaces become `_`; no dots or separators; max 60
characters; reserved Windows names prefixed with `_`). Clients never send paths. A clip is written to `<name>.part`
and renamed to `<name>` only after it is verified as WebM; an existing file is never replaced. The composite cloud
recording (§7) is unchanged and runs alongside where an egress worker exists.

| Endpoint | Auth | Notes |
|---|---|---|
| `POST /meetings/{id}/speech-recordings` | participant token or owner; admitted to the live session | Body `{ participantId, format: "video/webm" \| "audio/webm" }` → 201 `SpeechRecording` (status `RECORDING`). 409 if the meeting does not record automatically; 507 `INSUFFICIENT_STORAGE` when the disk is full. Starting while a clip is open closes that one (INCOMPLETE). |
| `PUT /meetings/{id}/speech-recordings/{rid}/chunks/{seq}?participantId=` | same; own clip only | Body: raw bytes (`application/octet-stream`, ≤ 8 MiB). `seq` starts at 0; a repeat of a stored chunk is ignored (200); a gap → 409; clip > 500 MiB → 413. A failed chunk leaves the file as it was. |
| `POST /meetings/{id}/speech-recordings/{rid}/finish` | same; own clip only | Body `{ participantId, chunks }`. `COMPLETED` only if every chunk arrived and the file verified as WebM; chunks missing → `INCOMPLETE` (kept); no valid media → `FAILED` (no file kept). Idempotent. |
| `GET /speech-recordings?view=hosted\|mine&date=YYYY-MM-DD&meetingId=&participantId=&page=&size=` | signed in | `hosted`: every clip of meetings you host; `mine`: clips of your own participations. `date` is the folder date. Newest first. |
| `GET /speech-recordings/facets?view=` | signed in | `{ meetings[], participants[], dates[] }` within what you may see. |
| `GET /speech-recordings/{rid}` | signed in; host or the participant | 404 for anyone else (existence not revealed). |
| `POST /speech-recordings/{rid}/access-url?download=` | signed in; host or the participant | `{ url, expiresAt }`: signed, valid 10 min; audited (`SPEECH_RECORDING_ACCESSED`). |
| `GET /speech-recordings/{rid}/content?expires=&download=&sig=` | the signature | Streams the file (Range supported), `Cache-Control: no-store`. |

`SpeechRecording`: `id, meetingId, meetingTitle, participantId, participantName, fileName, fileFormat, fileSize,
startTime, endTime, durationMs, status (RECORDING|COMPLETED|INCOMPLETE|FAILED), failureReason, createdAt`. The storage
path is never returned. A clip still `RECORDING` with no chunk for 2 minutes (browser gone, or a server restart) is
closed by a recovery job (at startup and every minute): what arrived becomes `INCOMPLETE`, nothing usable `FAILED`.

## 9. Chat and files (within a meeting)

| Method | Path | Body | Success |
|---|---|---|---|
| GET | `/meetings/{meetingId}/chat?before&limit` | — | `[ChatMessage]` |
| POST | `/meetings/{meetingId}/chat` | `{ participantId, text /* 1..4000 */ }` | `201 ChatMessage`; server relays via LiveKit data topic `chat` |
| GET | `/meetings/{meetingId}/files` | — | `[FileMeta]` |
| POST | `/meetings/{meetingId}/files` | multipart `file`, `participantId` | `201 FileMeta` (≤ 25 MB; allow-listed types; PDF, images, Office/ZIP must also start with their file signature, else `415 FILE_TYPE_NOT_ALLOWED`) |

`ChatMessage = { id, meetingId, participantId, senderName, text, sentAt }`

Participant-scoped calls (`leave`, `chat`, `files`, `local-recordings`, `join-status`) accept either the Bearer token of the
user that owns `participantId`, or header `X-Participant-Token: <waitToken>` (required for guests).
Reading chat history and files (`GET chat`, `GET files`, `download-url`) requires a participant that was **admitted** (and not
removed) — or a signed-in user who may view the meeting. The secret of a participant that is only waiting, or was denied or
removed, works for `join-status` and `leave` only (`403` elsewhere).

When `joinBeforeHost=false` and the host has not started the meeting, non-hosts receive `WAITING` and are admitted automatically
when the host joins (unless the waiting room is enabled, in which case the host admits them).

## 16. Real-time data channel contract (LiveKit data packets)

All payloads are UTF-8 JSON. Server-originated messages are sent with the LiveKit server API (clients cannot forge the sender as "server": they arrive with no participant).

| Topic | Payload | Sender |
|---|---|---|
| `chat` | `{ type: "chat", message: ChatMessage }` | server (after persisting) |
| `moderation` | `{ type: "request-unmute", source: "MICROPHONE" \| "CAMERA" }` | server → target identity |
| `moderation` | `{ type: "removed" }`, `{ type: "meeting-ended" }`, `{ type: "room-locked", locked }`, `{ type: "role-changed", participantId, role }`, `{ type: "waiting-room", count }` (hosts only), `{ type: "settings", screenSharePolicy }` | server |
| `recording` | `{ type: "recording", kind: "CLOUD" \| "PARTICIPANT" \| "LOCAL", state: "STARTED" \| "STOPPED" \| "FAILED", participantId?, displayName?, auto? }` | server |
| `files` | `{ type: "file", file: FileMeta }` | server (after upload) |
| `moderation` | `{ type: "settings", screenSharePolicy, chatEnabled }` | server |
| `reactions` | `{ type: "reaction", participantId, displayName, emoji }` — only 👍 👏 ❤️ 😂 😮 🎉 🙌 🤔 | server (relayed from `POST /signals/reaction`) |
| `hand` | `{ type: "hand", participantId, displayName, raised }` | server (relayed from `POST /signals/hand`) |
| `presence` | `{ type: "presence", count }` — people in the session (JOINED, one per person), read after the change commits; joins and leaves of one room within `app.meetings.presence-debounce` (default 250 ms) are sent as one update. In HOST_AND_SELF_ONLY numbered for the stage only; when the stage changes, attendees get an unnumbered `count` of their own (stage + themselves) | server |

**No participant may publish data** (`canPublishData=false` in every token): every packet on these topics comes from the server.

**Numbering.** Signals to the whole room carry `stream: "all", seq`; signals to the stage (host and co-hosts) carry `stream: "stage", seq` (a separate counter); signals to one participant carry no number. A client that sees a gap reloads `GET /meetings/{id}/room-state` (which returns the latest `seq` and, for the stage, `stageSeq`), and also reloads after a LiveKit reconnect.

**HOST_AND_SELF_ONLY (formerly HOSTS_ONLY; old names still accepted on input).** The session has a stage room (`roomName`; host/co-hosts publish, attendees subscribe-only and hidden) and one audience room per attendee (`<roomName>-aud-<participantId>`; the attendee's own is in its join response as `audienceRoomName` + `audienceToken`, and from `GET /audience-access`). An attendee publishes in its own room and may not subscribe; the stage joins every attendee's room hidden and subscribes. One room per attendee because the SFU tells every visible participant of a room who else is in it (identity, joins, mute state, speaking): attendees never share a room with another visible attendee. The SFU enforces all of it from the server-issued tokens; on every connection the server pushes the rights of the participant's current role (a token may carry an older role) and ejects anyone from an audience room that is neither its attendee nor the stage of that session. A demotion is announced to the stage and the person only. Attendees appear in the SFU as `Attendee` with metadata `{role}` only. An attendee's chat, hand, reactions and local-recording notices go to the stage (numbered, `stream: "stage"`) and to the attendee (unnumbered, so stage numbers reveal nothing about other attendees); chat messages written that way have `audience: "STAGE"`.
